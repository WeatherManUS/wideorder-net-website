# WideOrder automated production versions

## One counter and explicit phases

Production uses `vMAJOR.MINOR.RELEASE`, with exactly four release digits. The counter lives exclusively in `history.jsonl` on the repository's `release-history` branch. `CHANGELOG.md` on that branch is generated from the same events. Both are committed durably with every transition; neither depends on Hostinger's ephemeral filesystem. Do not edit, reset, force-push or delete that branch. The main-branch `releases/baseline.json` initializes it once; it is not another live counter.

The original verified `v0.1.0` baseline is normalized to `v0.1.0001`, retaining its original identifier, source commit, artifact ID and verified publication timestamp. The first new successful publication is `v0.1.0002`. `package.json` retains its npm package identity `0.1.0`; npm package versions do not allocate website releases. Local edits, local builds, development, previews, failed builds and failed reservations never advance the successful-production counter.

`release-policy.json` controls MAJOR and MINOR only. Never infer phase changes from commit text or the type of code change. For an explicitly authorized phase change, edit that file's `major` and `minor`, review/commit the change, then manually run the publication workflow with `authorize_phase` equal to the exact phase (for example `0.2`). A push alone cannot authorize a phase transition. The first publication in that phase is `0.2.0001`. MAJOR 1 requires explicit authorization. Phase decreases and release overflow past 9999 fail closed. Build fallback metadata is an unallocated identity, never a published release.

## Production lifecycle

Hostinger continues building the connected GitHub `main` branch with `npm run build`. No hosting, DNS or indexing setting changes are required. The release wrapper records build start separately from successful build completion, retains the Git commit/source fingerprint, generates a unique artifact UUID and preserves traced release metadata in standalone bundles. Failed builds cannot produce completed metadata.

`.github/workflows/publication.yml` runs after pushes to main or explicit workflow dispatch. It checks out trusted current workflow code, starts a durable attempt, and waits up to 25 minutes for Hostinger to serve the exact expected Git commit/artifact. It does not treat push acceptance, application startup or build completion as successful publication. It does not itself control Hostinger's build/start/traffic switch; the existing Hostinger Git integration still deploys the website.

Once the exact production artifact is reachable, the workflow reserves the next release in the ledger, bound to the Git commit, build ID and artifact UUID. The running server reads this reservation and exposes it as `verifying`, with a null publication timestamp. The verifier fetches uncached JSON and initial HTML, checks all release meta tags and the server-rendered footer, and only then appends a `published` event with a UTC success-observation timestamp. A final read verifies the publication timestamp, version, artifact and footer before reporting success. The workflow writes the requested **WideOrder Deployment** report to its job summary.

Until a reservation exists, production reports `version: "unallocated"`, `release: null`, `deploymentStatus: "awaiting-allocation"`, `publishedAt: null`. The footer says release awaiting allocation/publication, rather than assigning the older baseline to new code. Staging/development never consult or mutate the production counter. Set `RELEASE_ENVIRONMENT=staging` for previews running a production Next server.

## Concurrency, retries and failures

The workflow does not cancel running publication jobs when a later push arrives. GitHub may replace pending jobs; a job that never runs cannot allocate a release. The actual correctness boundary is the ledger's Git ref: append operations create a child commit and update the ref with `force: false`. Competing sibling writes cannot both fast-forward. A loser rereads/revalidates the winner before retrying. At most one unresolved production reservation is allowed, and rerunning verification of an already published artifact is idempotent.

Failed reservations remain in history as failed attempts; their provisional number is available for the next successful publication. Only successful publications own permanent release numbers, so failed attempts do not cause gaps. Attempt IDs are unique GitHub run/attempt identities; failed reservations are not advertised as successful releases. A second artifact cannot reserve a version while an earlier reservation is unresolved. If a run is forcibly killed before cleanup, the next verifier checks that exact GitHub run/attempt. Only a confirmed terminated failure/cancellation/timeout can be reconciled into a durable failed event before a new allocation. An active or unknown attempt continues to block allocation. Rerunning verification of the same artifact can also resume its reservation. Never delete events to unlock a reservation.

Failure/cancellation cleanup appends an event and preserves the last successful production record. A Hostinger build failure leaves the prior artifact live. If Hostinger switches traffic but public verification fails, this integration cannot automatically roll hosting back: the candidate remains explicitly unconfirmed, the ledger's successful-production pointer does not advance, and an operator must restore the previous complete Hostinger artifact. A final verification failure after a verified publication is recorded separately; it cannot erase or reuse a version already published. Hostinger logs remain the source for exact provider build/deployment errors. A timeout records failed verification, not an invented provider failure reason.

## Runtime identity, cache and visibility

`currentRelease()` supplies the endpoint, HTML release meta tags and server-rendered footer from one request-scoped value. It reads the allowlisted artifact identity and the corresponding public durable ledger record. Published artifact records are immutable and may be retained in process memory; after restart or rollback they are recovered from the ledger, without a local publication marker. Unpublished records are fetched uncached so verification can progress. No credential, database address or hosting detail is exposed. A remote-ledger outage before a publication is cached fails visibly rather than inventing a timestamp.

`/version.json` is public JSON, requires no JavaScript, and returns version, numeric major/minor/release, buildId, buildTime, publishedAt, environment and the observable deploymentStatus. The status reflects verification, not inaccessible Hostinger control-plane state. JSON and public HTML use `Cache-Control: no-store`; static assets retain normal caching. Release data appears in initial HTML without client-side insertion. `SHOW_FOOTER_VERSION=false` is the single runtime flag to hide the footer line; the endpoint/meta tags remain available.

Internally timestamps are UTC ISO 8601. The footer formats publication in America/Chicago, automatically choosing CST/CDT, and computes the copyright year automatically. Exact Hostinger traffic-switch timestamps are unavailable to this integration: publishedAt records the first successful public verification of the allocated version, not build time or a fabricated provider timestamp. Polling/network delay can separate that observation from the traffic switch.

## Verification and rollback

Check `https://wideorder.net/version.json`, then compare its build ID, version, artifact ID and timestamp with the initial HTML footer and wideorder-version/build/release meta tags. Run `node scripts/check-release.mjs https://wideorder.net` for fresh JSON, cache headers, HTML/JSON agreement across all 11 public content routes, repeated responses and anonymous callback rejection. Crawler HTTP 403 responses are reported separately from release checks. The publication workflow now requires visible matching footers on every public content route before and after publication. A successful workflow summary is required before claiming publication. A mismatch identifies old/cached HTML or an unconfirmed deployment; do not manually patch dates or counters.

Rollback restores an existing complete Hostinger artifact. The artifact's original UUID selects its original durable version and publication time, even if local publication files were lost. Run the current main-branch workflow with `release_ref` set to that artifact's original Git commit/tag to record a rollback verification event with previous active version and rollback reference. The workflow does not perform the hosting rollback. A tracked rollback never increments RELEASE. A rebuild gets a new UUID and correctly becomes a new release. Legacy artifacts predating this policy retain their legacy metadata; rebuild them with policy support for durable tracked rollback.

Validation: `npm run lint`, `npm run typecheck`, `npm run build`; native Node tests in `src/lib/release/*.test.mjs` cover real rejected Git fast-forward races, failed reservations, phase transitions, overflow, durable rollback recovery, Chicago formatting and HTML agreement. Browser QA remains in `scripts/appearance-footer-qa.mjs`; against production use `QA_BASE_URL=https://wideorder.net`, existing `PLAYWRIGHT_MODULE_PATH`, and no local fixture seeding. The legacy local-publication fixture flag is rejected for policy-managed artifacts.

References: [GitHub atomic fast-forward reference updates](https://docs.github.com/en/rest/git/refs), [GitHub concurrency behavior](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency). The release workflow changes only its own durable ledger branch; it does not push release-history commits into main or trigger a deployment loop.
